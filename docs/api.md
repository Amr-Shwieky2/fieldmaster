# API Reference

Full interactive documentation: `GET /api/v1/docs` (Swagger UI) once the
API is running (`pnpm dev` or `docker compose up`). This document covers
conventions the Swagger UI doesn't make obvious at a glance.

## Base path and route groups

Everything is under `/api/v1`. Implemented route groups:

```text
/auth                  OTP request/verify, refresh, logout
/organizations         org settings: GET /me/settings; PATCH /me/settings/workday|onboarding|notifications (Owner, audited)
/memberships           members, roles, suspend/reactivate/archive, time tracking, devices and sessions (Owner)
/workers                roster, onboarding approval/rejection; /:id/estimated-earnings and
                        /:id/onboarding-review (Owner only)
/onboarding-invitations single-use invite links (Step 8): create (the token is returned once), list
                        with status, DELETE /:id revokes
/onboarding/invitations/:token  the public join page (no sign-in, rate limited): page data,
                        /uploads, /redeem
/file-assets            /:id/view-url: a 60 s signed URL of an ID document or photo (Owner only, audited)
/compensation-profiles  effective-dated rate profiles
/projects, /sites, /geofences
/shifts, /shift-assignments
/temporary-supervisors  the supervisor's own API: /me, /:assignmentId/shift, /:assignmentId/report-issue (checked live)
/shifts/:id/temporary-supervisors  assign / list (managers); /shifts/temporary-check-in-points open / close
/operations            /live: the live operations snapshot (Owner, Field Manager; no money)
/clock-events           clock-in / clock-out (online)
/devices                Ed25519 public-key registration for offline signing; PUT /me registers the signed-in
                        device (platform, OS / app version, push token), Step 9
/attachments            Step 9: attendance photos and voice summaries from the mobile app (private);
                        /:id/transcription
/offline-sync           batched offline clock-event submission
/time-entries           attendance detail, approvals, corrections; /:id/evidence (detail page);
                        /:id/estimated-cost (Owner only)
/attendance/entries     admin attendance list: tabs, filters, page-based pagination
/forgotten-stamp-infractions  month list; Owner-only reversal
/turan-assignments, /emergency-callouts (start/end, plus the admin list and detail)
/payroll-periods         Owner only (Step 7): months and their versions (/:yearMonth = latest,
                        /:yearMonth/versions[/:version[/workers/:workerProfileId]]), calculate (202, a
                        background job; /:yearMonth/calculation = its state), finalize, reopen (reason),
                        adjustments (manual +/-), dashboard; /:yearMonth/my-payslip (own, finalized only)
/payroll-statements/me  the caller's own monthly statements (finalized) + a labeled estimate
/reports                Step 8: seven report types as Arabic PDF + CSV, generated by a background job:
                        POST (Idempotency-Key, 202), list, details, /:id/download?format=pdf|csv, /:id/verify
/notifications          in-app list, mark-read, WebSocket/SSE streams
/audit-logs              paginated list + chain verification
/dev                     test-mode tools for the worker simulator (dev login only; 404 otherwise)
```

Not implemented as separate route groups (see `IMPLEMENTATION_STATUS.md`):
`/sessions` (folded into `/auth`) and `/settings` (under
`/organizations/me/settings`). There is no general `/files` upload group:
files are uploaded only on the public onboarding page and read through
`/file-assets/:id/view-url`.
`/forgotten-stamp-infractions` has no CRUD surface: infractions are created
by manual corrections, and the group only lists them and reverses a
deduction.

Money for the attendance screens never appears in the attendance list,
evidence or emergency responses of a Field Manager. An Owner gets it from
`GET /time-entries/:id/estimated-cost` and
`GET /workers/:id/estimated-earnings?month=YYYY-MM` (both
`VIEW_COMPENSATION`), and from `estimatedCostAgorot`, which only an Owner's
emergency call-out DTO has. See `authorization-matrix.md`.

## Payroll (Step 7)

- **Versions.** A month's payroll is a chain of versions. `GET
  /payroll-periods/:yearMonth` is the latest (working, or the last
  finalized); `GET .../versions/:version` any of them. A version is always
  read from its stored calculation (inputs, per-worker and per-entry
  results, totals): finalized versions never change (the database refuses
  it), and reopening (`POST .../reopen { reason }`, Owner) creates the next
  version.
- **Calculation is a background job.** `POST .../calculate` with an
  `Idempotency-Key` answers `202` with the run (`QUEUED`); poll `GET
  .../calculation` for `state` (`QUEUED` / `RUNNING` / `SUCCEEDED` /
  `FAILED`), `progress` (0-100), `processedWorkers` / `totalWorkers` and,
  when it failed, `errorCode`. The same key always answers the same run
  (even after it finished); a second calculation while one is queued or
  running is `409 PAYROLL_CALCULATION_IN_PROGRESS`; a finalized version is
  `409 PAYROLL_PERIOD_FINALIZED`.
- **Errors:** `PAYROLL_PERIOD_NOT_READY` (finalize before a calculation),
  `PAYROLL_PERIOD_NOT_FINALIZED` (reopen a version that is not finalized).
  A malformed `:yearMonth` is a 400; an unknown `:version` a 404.
- **Money keys** end in `Agorot` (integer agorot), so the financial leak
  scanner flags them on any route that is not Owner-only.

## Onboarding (Step 8)

- **Invitations** (`APPROVE_ONBOARDING`: Owners and Field Managers).
  - `POST /onboarding-invitations { prefilledPhoneNumber? }` answers
    `{ invitationId, token, joinPath, expiresAt }`. This is the only time
    the token leaves the API: only its SHA-256 is stored.
  - `GET /onboarding-invitations` lists them with a derived `status`:
    `ACTIVE`, `USED`, `EXPIRED` or `REVOKED`.
  - `DELETE /onboarding-invitations/:id` revokes. A used one is
    `409 INVITATION_ALREADY_USED`; revoking an already revoked or expired
    one changes nothing.
- **The public page** (`@Public`, no session; `ONBOARDING_RATE_LIMIT`
  requests per minute per IP and route, default 10):
  - `GET /onboarding/invitations/:token`: organization name, prefilled
    phone, expiry, privacy notice version, upload limits.
  - `POST …/:token/uploads`: multipart `purpose` (`IDENTITY_DOCUMENT` or
    `PROFILE_PHOTO`) and `file`. It answers `{ fileAssetId, purpose,
    contentType, sizeBytes }`, or one of:
    - `413 FILE_TOO_LARGE` (`details.maxBytes`);
    - `415 FILE_TYPE_NOT_ALLOWED` (`details.allowedContentTypes`; typed by
      content);
    - `422 FILE_REJECTED` (malware hook);
    - `429 RATE_LIMITED` (also after 20 files on one link).
  - `POST …/:token/redeem`: the application. It answers only
    `{ submitted: true }`; the errors are:
    - `400 VALIDATION_FAILED`, where `details.field` names
      `governmentIdNumber` (checked by its type's rule) or `phoneNumber`
      (it must equal a prefilled phone);
    - `400 UPLOAD_NOT_FOUND` (`details.field`: the upload id that is not
      this link's);
    - `409 CONFLICT` (the phone already has a membership here).
  - Every unusable link (unknown, malformed, used, expired, revoked) is the
    same `404 INVITATION_INVALID_OR_EXPIRED`.
- **The Owner's review** (`VIEW_BANK_INFO`, Owner only,
  `Cache-Control: no-store`, every call audited):
  - `GET /workers/:id/onboarding-review` returns the application with the
    ID number and bank details decrypted.
  - `GET /file-assets/:id/view-url` returns
    `{ url, expiresInSeconds: 60, contentType }`, served inline.
  - Approve with `POST /workers/:id/approve { compensationProfile }`;
    reject with `POST /workers/:id/reject { reason }` (not blank).

## Reports (Step 8)

- **Request:** `POST /reports { reportType, filters }` with an
  `Idempotency-Key` answers `202` with the report (`QUEUED`). Poll
  `GET /reports/:id` until `status` is `READY` or `FAILED`; `progress` goes
  0-100. The same key always answers the same report; a key reused for a
  different request, or by someone else, is `409 IDEMPOTENCY_KEY_CONFLICT`.
- **Errors on request:**
  - `400 VALIDATION_FAILED`: filters that do not fit the type;
  - `403`: the caller may not request this type;
  - `404`: a worker, project, site or payroll version outside the caller's
    organization.
- **Types and filters:**

  | Type | Filters |
  |---|---|
  | `WORKER_ATTENDANCE_LEDGER` | `workerProfileId`, `fromDate`, `toDate` |
  | `OPERATIONAL_ATTENDANCE`, `OVERTIME`, `SITE_VIOLATIONS` | `fromDate`, `toDate`; optional `projectId`, `siteId`, `workerProfileId` |
  | `EMERGENCY_CALLOUTS` | `fromDate`, `toDate`; optional `workerProfileId` |
  | `FORGOTTEN_STAMPS` | `fromDate` + `toDate`, or `yearMonth`; optional `workerProfileId` |
  | `PAYROLL` | `yearMonth`; optional `version` (default: the latest) |

  Dates are business dates (`YYYY-MM-DD`, Asia/Jerusalem), inclusive, at
  most 366 days apart.
- **Who gets which version:** see `authorization-matrix.md`. The answer's
  `includesFinancials` says which copy was generated.
- **Files:**
  - `GET /reports/:id/download?format=pdf|csv` answers
    `{ downloadUrl, expiresInSeconds: 300, fileName, sha256 }`. The URL is
    signed, private, served as an attachment with an Arabic file name, and
    every download is audited.
  - A report that is not READY is `409 REPORT_NOT_READY`.
- **Verify:** `GET /reports/:id/verify` reads both stored files back,
  hashes them again and compares with the hashes recorded at generation:
  `{ valid, dataSha256, files: [{ format, expectedSha256, actualSha256,
  matches }] }`. A changed or missing file is `valid: false`, never an
  error. Every check is audited.
- **Visibility:** a report the caller may not see is a 404 on every
  `/reports/:id*` route, as if it did not exist.
- **Files' content:**
  - PDF: Arabic, right to left, with an embedded font; Western digits,
    Asia/Jerusalem times, amounts as `1,234.50 ₪`. Every page's footer has
    «صفحة N من M», the report ID and the SHA-256 of the report's data.
  - CSV: UTF-8 with a BOM, Arabic headers, Western digits; amounts as plain
    numbers in shekels with two decimals, in financial copies only.

## The mobile worker app (Step 9)

- **Device:** `PUT /devices/me { deviceId, platform: IOS|ANDROID|WEB,
  osVersion, appVersion, pushToken, attestationState? }` answers
  `{ deviceId, platform, keyStatus: NONE|ACTIVE|REVOKED, registeredAt }`.
  - It is an upsert for the caller's (user, device). A field left out keeps
    its value; `null` clears it.
  - A push token (`ExponentPushToken[…]`) lives on one device row only.
  - `POST /auth/logout` clears the device's push token.
- **Attachments:** `POST /attachments` (multipart `purpose` =
  `ATTENDANCE_PHOTO` | `VOICE_SUMMARY`, `file`), for members with a worker
  profile.
  - Answers `{ fileAssetId, purpose, contentType, sizeBytes }`.
  - The type comes from the content: photos JPEG/PNG (metadata removed);
    voice MP4/M4A, WebM, Ogg, WAV or MP3.
  - Refusals: `413 FILE_TOO_LARGE` (10 MB), `415 FILE_TYPE_NOT_ALLOWED`,
    `422 FILE_REJECTED`, `429 RATE_LIMITED` (50 uploads not yet attached).
  - `POST /attachments/:id/transcription` (the caller's own voice summary)
    answers `{ text, provider, language: "ar" }`, or
    `503 TRANSCRIPTION_UNAVAILABLE` (`TRANSCRIPTION_PROVIDER=none`, the
    production default).
- **Clock-in / clock-out** also take:
  - `photoAssetIds` (up to 5 of the caller's unused photo uploads),
    `mockLocationState` (DETECTED / NOT_DETECTED / UNAVAILABLE) and
    `locationSignals` (recorded, never a refusal);
  - clock-out only: `summarySource` (TYPED / VOICE), `voiceNoteAssetId` and
    `transcription`.

  Rules and errors:
  - DETECTED is refused like `mockLocationSuspected` (`403
    MOCK_LOCATION_BLOCKED`).
  - A text summary or a voice note is still required (`400
    SUMMARY_REQUIRED`).
  - A foreign, used or unknown upload is `400 UPLOAD_NOT_FOUND`
    (`details.field`).
  - Both answers carry the receipt: the clock event (reference id, server
    and device times), the shift and the entry.
- **Emergency:** `GET /emergency-callouts/eligibility` answers `{ eligible,
  reason, turanAssignment, activeCallout }` with the same checks as
  `start`, without creating anything.
- **The worker's own entries:**
  - `GET /time-entries?month=YYYY-MM`.
  - `GET /time-entries/:id`, for one's own entry: corrections with reason
    and name, the summary and the photo count; another worker's entry is
    404.
  - `GET /time-entries/:id/my-pay`: one's own entry only. No amount until
    it is approved. A finalized month's figures come from its finalized
    version.
- **Salary:** `GET /payroll-statements/me/current` gives the open month as
  an estimate (`basis: APPROVED_ENTRIES_ONLY`, `pendingEntries`). Once the
  month has a finalized version it is `409 PAYROLL_PERIOD_FINALIZED`, and
  the month is then in `/payroll-statements/me`.
- **Notifications:**
  - `GET/PATCH /notifications/preferences` (`{ preferences: [{ type, push
    }] }`, the types the caller's role receives; push on by default).
  - `POST /notifications/read-all`.
  - Push follows the preferences. In-app notifications are always kept.
- **Sign-in states:** after a correct code, an account without an active
  membership gets `403 ACCOUNT_PENDING_APPROVAL`, `ACCOUNT_SUSPENDED` or
  `ACCOUNT_REJECTED`. Requesting a code, or a wrong code, looks the same
  for every number.
- **Revoked device keys:**
  - An offline event signed with a revoked key is rejected with
    `DEVICE_KEY_REVOKED`.
  - A new key for that device is accepted only from a session that started
    after the revocation.
- **Shift detail for a worker** (`GET /shifts/:id`): project, site (with
  instructions and position), geofence, check-in method, the manager's
  name, and only the temporary points usable now. Only the worker's own
  assignment is included, never co-workers' names or phone numbers (the
  list `GET /shifts` likewise).

## Real-time

- **WebSocket:** socket.io namespace `/notifications`, with the access token
  as `auth.token` or `?token=`.
- **SSE fallback:** `GET /notifications/stream?token=`.
- **Authentication:** both check the token like a REST call: an active
  membership and a session that hasn't been revoked.
- **Events:**
  - `notification` (SSE: the default message event): the caller's new
    notification;
  - `operations` (Owners and Field Managers, Step 6): `{ kind, at }`, a
    signal to refetch `GET /operations/live`;
  - SSE only: `ping` every 25 s.
- **When connections close:** both end when the member is suspended or
  archived, their role changes, or the session is revoked.

## Authentication

Phone number + OTP. `POST /auth/otp/request` (dev: code printed to the API
log via `ConsoleOtpProvider`; production: Twilio Verify, untested against a
live account here) → `POST /auth/otp/verify` returns a short-lived JWT
access token and a rotating opaque refresh token (`familyId:secret`).
Refresh-token **reuse** (a secret that doesn't match the family's current
hash) revokes the entire session family immediately — this is deliberate
theft detection, not a bug, so a genuinely stale client will need to log in
again rather than silently recovering.

A user belonging to more than one organization gets `400
ORGANIZATION_SELECTION_REQUIRED` with the candidate list on their first
verify call; resubmit with `organizationId` to disambiguate.

## Error format

Every error response has this exact shape, produced by a global
`AllExceptionsFilter` regardless of where in the stack it originated:

```json
{
  "statusCode": 400,
  "code": "GEOFENCE_OUTSIDE_ALLOWED_RADIUS",
  "message": "You are outside the permitted check-in area.",
  "details": { "distanceMeters": 184, "allowedRadiusMeters": 100 },
  "correlationId": "..."
}
```

`code` is a stable machine-readable identifier
(`apps/api/src/common/errors/app-exception.ts`); `message` is safe to show
a worker directly. Stack traces never appear in a response body. The admin
web is Arabic only and never displays `message`: it shows the Arabic text
for `code` (or for the HTTP status when it doesn't know the code), and its
`pnpm lint` fails if a code the API can send has no Arabic message.

## Idempotency

Required (`Idempotency-Key` header) on: clock-in, clock-out, offline-sync
batch submission, payroll calculation (the key identifies the background
run), and report requests (`POST /reports`; the key identifies the report). Implementation:
`IdempotencyService.withIdempotency(key, route, body, handler)` hashes the
request body, stores it keyed by `(key, route)`, and replays the stored
response on an exact retry; a retry with the same key but a *different*
body is rejected with `409 IDEMPOTENCY_KEY_CONFLICT`.

## Pagination

Cursor-based on high-volume lists (`/audit-logs`): response shape is
`{ items, nextCursor }`, pass `nextCursor` back as `?cursor=...` for the
next page.

Page-based on the admin attendance lists (`GET /attendance/entries`,
`GET /emergency-callouts`):
- `?page=` (from 1) and `?pageSize=` (default 20, at most 100);
- response shape `{ items, page, pageSize, total }`;
- `/attendance/entries` adds `tabCounts` (`PENDING`, `APPROVED`,
  `REJECTED`, `ALL`) under the same filters;
- a page past the end returns `items: []` with the real `total`;
- filters are validated (UUIDs, `YYYY-MM-DD` business dates, enum values)
  and an invalid value is a 400.

Other list endpoints (workers, shifts, sites) are simple arrays: the data
volumes in this deployment shape don't yet justify pagination there.

## Offline sync specifics

See `offline-sync.md` for the full protocol. In short:
`POST /devices/public-key` registers a device's signing key once;
`POST /offline-sync/batches` submits an array of signed events (processed
in device-timestamp order) and returns a per-event outcome
(`VERIFIED`/`FLAGGED`/`REJECTED`/`DUPLICATE`), never a single pass/fail for
the whole batch.

## Rate limiting

A global `@nestjs/throttler` rule (300 requests/minute per client and route;
over it, `429 RATE_LIMITED`) plus a stricter, separate limit on OTP requests
(5 per 15-minute window per phone number, enforced in
`AuthService.requestOtp`). The public onboarding routes have their own
limit (Step 8): `ONBOARDING_RATE_LIMIT` requests per minute per IP address
and route (default 10). Behind a proxy or load balancer, configure Express's
`trust proxy` so the limit sees the client's address rather than the
proxy's (see `deployment.md`).
